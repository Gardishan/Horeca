# Тест HoReCa KZ для команды и знакомых

На 29.09.2026 стенд доступен для личного ознакомления владельца, но перед раздачей группе нужно доставить source-исправление обхода приглашения из PR #58 и проверить исправленную версию на сервере. Ремонт восьми demo PDF уже выполнен отдельно, без замены application image. [Аудит и известные дефекты](MVP_BETA_AUDIT_2026-09-29.md). Ниже — готовый сценарий группового прохода после исправления; это не утверждение о завершённом релизе.

## Доступ

Сайт: https://horeca-beta.up.railway.app/catalog — браузер на компьютере или телефоне. Приложение устанавливать не обязательно.

1. Организатор выдаёт код приглашения лично из своего защищённого хранилища; содержимое не включается в репозиторий или отчёты.
2. Ввести код на странице «Код приглашения». Доступ этого браузера действует до 8 часов.
3. Для покупателя больше ничего не нужно. Для кабинета открыть `/login`: **Active Supplier**, **Pending Supplier**, **Demo Admin**. Для смены роли нажать «Выйти», дождаться каталога, затем снова открыть `/login`.
4. Если на телефоне пока не видна ссылка в кабинет, открыть `/dashboard/company` для поставщика или `/admin` для администратора. Это обход известного дефекта, который должен быть исправлен.

Каждый приглашённый имеет доступ ко всем demo-ролям, включая администратора. Раздача кода — приглашение в общий тестовый стенд, а не выдача отдельного персонального кабинета. Не публикуйте код и не добавляйте его в URL или скриншоты.

## Что отправить участнику

> Проверяем demo-версию HoReCa KZ: https://horeca-beta.up.railway.app/catalog. Код пришлю отдельно. Это общий стенд команды; используйте только вымышленные компании, контакты и документы, ничего не оплачивайте. Пройдите сценарий ниже на компьютере и телефоне. Ошибки и непонятные места присылайте мне в этой переписке: роль, страница, шаги, ожидаемый результат и что получилось. Не меняйте административные статусы до отдельного совместного прохода.

Организатору достаточно использовать существующую переписку с участниками и вести один список замечаний. Новый чат-бот, support-модуль или подписка для этого не нужны.

## Основной проход

Рекомендуемый формат — короткие отдельные сессии; роль администратора проверять после buyer/supplier-прохода. Это организация теста, не новый лимит приложения.

| Шаг | Действие | Что должно получиться |
|---|---|---|
| 1. Приглашение | Открыть ссылку в приватном окне; ввести выданный код | До кода — приглашение; после — каталог с предупреждением о demo Beta |
| 2. Каталог | Найти кофе, применить фильтр, открыть товар | Понятны товар, цена, MOQ, поставщик и доставка; недоступный результат поиска имеет empty state |
| 3. Заявка | Открыть `/catalog/arabica-blend-1kg`; отправить запрос с уникальным комментарием | «Запрос отправлен»; нет требования платить или регистрироваться покупателю |
| 4. Поставщик | Войти как Active Supplier → `/dashboard/requests` | Видны та же заявка, количество, комментарий и синтетические контакты |
| 5. Чужая компания | Выйти, выбрать Pending Supplier → заявки | Заявка предыдущей компании не видна |
| 6. Кабинет | Открыть профиль, billing, verification и товары | Понятны статус компании, следующий шаг, условия публикации; заполнение само по себе не активирует компанию |
| 7. Телефон | Повторить каталог → товар → кабинет на узком экране | Нет прокрутки всей страницы вбок; формы, ошибки, меню и возврат в кабинет доступны |
| 8. Администратор | Demo Admin → `/admin/company/company-pending`; просмотреть документы и журнал | Demo PDF скачивается только в этой роли; действие видно в журнале; нет прямых storage URLs |

Синтетические данные для заявки: имя «Тестовый покупатель», компания `Demo QA T01`, телефон `+70000000000`, email `qa+t01@example.test`, количество 12. Комментарий — «Тест T01 — 29.09 — заявка из браузера». Следующий участник использует другой маркер, чтобы отличить свою заявку.

Не звоните и не отправляйте email по demo-контактам. Появление заявки в inbox — конечный результат текущего сценария; автоматического письма или встроенного ответа здесь нет.

## Проверка решений администратора

Выполнять последовательно с организатором, по [подробной инструкции](BETA_GUIDE.md#demo-admin-ручные-решения). Сначала договориться, какую запись одобряем, а какую отклоняем. Администратор отдельно решает вопросы документов, оплаты, verification и активации компании.

Данные общие, terminal decisions нельзя обратить противоположной кнопкой. Повторный запуск seed не возвращает всё к начальному состоянию. Не блокировать основной Active Supplier и не менять его опубликованные товары в обычном проходе: это повлияет на других участников.

Настоящие реквизиты, договоры, документы, персональные данные и платежи не используются. Demo-checkbox — подтверждение участника; приложение не умеет распознавать все реальные данные внутри файла.

## Отрицательные сценарии и ограничения

- В отдельном приватном окне без кода обычный каталог должен вести к приглашению. Техническую проверку обхода через headers выполняет инженер до раздачи стенда.
- Поставщик не должен получать административные данные и скачивать приватные admin-документы. Pending Supplier не должен публиковать товар без выполнения условий.
- После доставки source-исправления F2: обрыв сети или не-JSON ответ должны дать понятную ошибку и доступную повторную попытку с сохранённым вводом. На прежнем runtime известен вечный busy; refresh снимает его, но может потерять ввод. Если ответ на заявку потерян, сначала уточнить получение у поставщика; организатор может проверить общий demo inbox.
- Один офис/Wi-Fi может разделять rate limit: login 10/10 минут, invite 10/15 минут, заявки 8/час. При 429 подождать указанный срок, записать ситуацию и не создавать поток повторов.
- Самостоятельная регистрация закрыта. Android APK — debug; обычный Quality APK направлен в локальный эмулятор. Для первого прохода используйте браузер; APK выдаётся отдельно из согласованного Beta Launch.

Фиксируйте также места, где пришлось объяснять интерфейс: успешный сценарий с постоянными подсказками ещё не подтверждает удобство продукта.
